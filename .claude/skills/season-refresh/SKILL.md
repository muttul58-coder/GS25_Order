# 시즌 갱신 — 링크 두 개로 시작하기

관리자(양창호 님)는 1년에 두 번, **카탈로그 사이트 주소**와 **바코드북 PDF** 두 가지만
건넨다. 나머지는 이 절차대로 진행한다. 배경 지식은 `CLAUDE.md` 의
"Seasonal Catalog Refresh" 절에 있고, 관리자용 설명은 `docs/관리자안내.md` 다.

**한국어로 대화한다.** 관리자는 개발자가 아니다. 파일 이름과 명령어는 그대로 쓰되,
설명은 "무엇이 어떻게 되는지" 위주로 짧게 적는다.

## 0단계 — 준비 (한 번에 다 본다)

```bash
python tools/season_prep.py <카탈로그 주소> <바코드 PDF 파일 또는 링크>
```

카탈로그 주소는 `https://gs25mobile.com/2027_1st/category` 처럼 어떤 형태로 받아도 된다
(스크립트가 `/products.json` 으로 다듬는다). PDF 가 링크면 받아서 `BarcodeSource/` 에 넣고,
로컬 파일이면 그 폴더로 복사한다.

이 한 번으로 다음이 모두 나온다.

- 카탈로그가 열리는지, 상품 수, 시세반영 상품
- 카탈로그 항목 이름이 우리가 아는 모양인지 (`price` → `amount` 같은 변경이면 여기서 멈춘다)
- **사전행사 배너 그림**이 `.season_prep/` 에 저장됨 → 다음 단계에서 읽는다
- 처음 보는 **구매혜택 아이콘**만 골라 같은 폴더에 저장
- PDF ↔ 카탈로그 상품코드가 1:1인지
- **택배 배송이 안 되는 분류(주류)** 를 분류 이름에서 찾았는지
- `시즌설정.txt` 에 넣을 초안 (날짜 3줄만 비어 있음)

멈추거나 `[!]` 가 나오면 **그 자리에서 관리자에게 알린다.** 뒤 단계로 넘어가지 않는다.

## 1단계 — 행사 날짜 읽기

`.season_prep/headers_event_header_1.png` 와 `events_event_1.jpg` 를 Read 로 **직접 본다.**
날짜는 그림 안에 글자로만 있어서 코드로는 못 읽는다.

배너 예시: `2026.08.17(월) ~ 2026.09.04(금), 19일간 / 삼성·KB국민·비씨·신한카드`

| 시즌설정.txt | 어디서 |
|---|---|
| `사전행사 시작` | 배너의 시작일 |
| `본행사 시작` | 배너의 **끝난 날 + 1일** ← 배너에 안 적혀 있다 |
| `사전행사 조건` | 카드 조건 문구 그대로 |

배너에 "총 ○○품목" 같은 숫자가 있으면 적어 둔다. 3단계 실행 결과의 사전행사 품목 수와
같아야 하는 공짜 검산이다.

**읽은 날짜 3가지를 관리자에게 먼저 확인받는다.** 배너 문구는 시즌마다 표현이 달라지고,
날짜를 틀리면 행사가 통째로 어긋난다. 여기서만 한 번 물어보면 나머지는 쭉 진행된다.

## 2단계 — 처음 보는 구매혜택 아이콘

0단계가 `[!] ○번 - 처음 보는 아이콘` 을 냈을 때만 해당한다. 없으면 건너뛴다.

`.season_prep/benefit_<번호>.png` 를 Read 로 본다. 읽은 비율을 `시즌설정.txt` 맨 아래에
`구매혜택 37: 2+1` / 덤이 아니면 `구매혜택 41: 없음` 으로 적는다.

**★ 반드시 그림과 함께 관리자에게 확인받는다.** 실제 `2+1` 과 `3+1` 아이콘은 글자 하나만
다르다. 잘못 읽으면 조용히 틀린 수량이 나가고, 점원이 약속한 덤을 매장이 물어줘야 한다.
읽은 값을 단정하지 말고 "이렇게 보이는데 맞습니까" 로 묻는다.

아이콘에 `9월 5일부터` 같은 날짜가 함께 그려져 있어도 **비율만** 적는다.

## 3단계 — 시즌설정.txt 고치고 실행

0단계가 만들어 준 초안 + 1·2단계에서 확인받은 값으로 `시즌설정.txt` 를 고친다.
매장 3줄(이름·담당자·전화)과 `응답 시트 주소` 는 시즌과 무관하므로 건드리지 않는다.

실행 방법은 **관리자에게 고르게 한다.**

- **권장 — 관리자가 GitHub 에서 버튼을 누른다.** 설정 파일과 PDF만 커밋해 두고,
  관리자가 [시즌 갱신 워크플로](https://github.com/muttul58-coder/GS25_Order/actions/workflows/season-update.yml)
  에서 실행한다. 1년에 한 번 관리자 경로가 살아 있는지 확인되고, 실행 기록에
  상품 수·품목 수가 남아 검산이 된다.
- 급하면 로컬에서 `python tools/update_season.py` (바코드 601장 렌더링에 3~5분).
  `--skip-barcodes` 는 PDF 가 그대로일 때만 쓴다.

`--allow-name-mismatch` 와 `--allow-unknown-benefits` 는 **쓰지 않는다.** 그 검사들이
멈추는 상황은 전부 "종이와 화면이 다른 물건을 가리킬 수 있다" 는 뜻이다.

## 4단계 — 확인하고 넘긴다

실행 결과에서 이것들을 직접 확인하고 관리자에게 숫자로 보고한다.

- `[OK] PDF ↔ 카탈로그 상품 ○개 이름까지 일치`
- `[OK] 상품 ○개 ↔ 바코드 ○개 완전 일치`
- 사전행사 품목 수 ↔ 1단계에서 적어 둔 배너의 "총 ○○품목"
- `배송 불가(주류): ○품목 · <분류 이름>` — 분류 이름이 술 묶음이 맞는지 눈으로 본다
- `admin.html` 을 띄워 시즌 이름·행사 기간·상품 수가 새 값인지 (미리보기 서버 이용)

주류 분류를 자동으로 못 찾으면 3단계가 **아무것도 만들지 않고 멈춘다.** 그때는
실행 기록이 찍어 준 이번 시즌 분류 이름을 **관리자에게 보여 주고 확인받은 뒤**
`시즌설정.txt` 에 `배송불가 분류:` 한 줄을 넣는다. 임의로 고르지 않는다 — 술이 아닌
분류를 넣으면 멀쩡한 상품이 배송 불가가 되고, 빠뜨리면 술이 배송된다.

그리고 **관리자만 할 수 있는 한 가지를 반드시 남긴다.**

> ★ 인쇄해서 실제 스캐너로 바코드를 찍어보셔야 합니다.

대신 해 줄 수 없다. 카탈로그 JSON 에 바코드 번호 필드가 없어서 대조할 정답이
아예 없다 — 바코드의 정답은 PDF 안에만 있고, 우리가 만드는 이미지도 그 PDF 에서
잘라낸 것이라 자기 자신과 비교하는 꼴이 된다. 명절마다 같은 코드가 다른 상품을
가리키므로(2026 추석: 371개), 스캔해 보지 않으면 화면상으로는 아무 문제가 없어 보인다.

## 하지 말 것

- `products.js` · `store.js` · `BarcodeImgs/` 를 손으로 고치기 (전부 생성물)
- `season.json` 을 손으로 고치기 (아이콘 그림 기억. 스크립트가 관리한다)
- 시즌마다 달라지는 값을 `admin.html` 이나 JS 에 적어 넣기 (다음 시즌에 거짓말이 된다)
- 확인 없이 커밋·푸시 (관리자가 요청할 때만 한다)
